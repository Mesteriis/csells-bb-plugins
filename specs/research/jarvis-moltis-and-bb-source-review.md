# Moltis and existing BB Jarvis: source review

Reviewed 2026-11-14, before implementation. These are source observations and design recommendations, not fresh runtime passes. Moltis was fetched into task-owned research storage without installing or executing it. BB Jarvis was read directly from the fetched `origin/eli` tree. No upstream code has yet been copied into the candidate.

## Source selection and provenance

## Moltis: execution and approvals

The nonblocking spawn path allocates a task ID, stores its session scope and abort handle, runs the agent in an `Abortable` future, and returns independently of completion. Tools are filtered and session identity is propagated to child tools. The separate task store exposes status, result and cancel. This is a concrete example of keeping conversation free while work runs. [Spawn implementation](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/crates/tools/src/spawn_agent.rs#L550)

The task store checks session access before cancel, marks cancellation, and aborts its stored future. Completion refuses to overwrite an already-cancelled state. Those are useful invariants. However, the inspected store uses in-memory maps, and cancel sets its terminal status before awaiting any evidence of external process death. Neither fact satisfies our durable-recovery or verified-process-termination contract by itself. Port the ownership check and terminal-state monotonicity, while keeping a distinct `cancelling`/unconfirmed phase until BB and actual process evidence agree. [Task store](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/crates/tools/src/spawn_agent_tasks.rs#L148)

Approval requests get opaque UUIDs, a session key, original command and a one-shot response channel; timed-out or closed channels do not grant permission. This is useful request binding. The gateway resolver nevertheless returns `{ok:true}` after calling a manager whose unknown-ID behavior is a warning, and configuration setters in that gateway service return empty success without mutation. Jarvis should preserve the request-ID pattern while reporting applied, stale, already answered and unsupported outcomes explicitly. Approval-mode and command allowlist behavior must be evaluated at the actual execution boundary, not inferred from the existence of the UI. [Approval manager](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/crates/tools/src/approval.rs#L632), [gateway service](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/crates/gateway/src/approval.rs#L27)

Source tests include session-scoped cancellation and timeout behavior; they are useful scenario donors. This review did not run them or verify subprocess termination. [Task tests](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/crates/tools/src/spawn_agent_tasks.rs#L639), [spawn timeout test](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/crates/tools/src/spawn_agent_tests.rs#L795)

## Moltis: memory and initiative

Its documented surfaces separate session control state, managed user profile, prompt memory, searchable memory, user files and attachments. In particular, adding a user-managed file does not automatically ingest it into memory. Independent controls govern retrieval, agent writes, profile writes and transcript export. Jarvis should retain this separation without copying the number of settings or file layout. BB already owns the transcript and workspace; plugin memory should store sourced personal facts and retrieve history deliberately. [Memory surfaces](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/docs/src/memory-surfaces.md)

Natural-language forgetting is split into candidate selection, model planning, deterministic validation and mutation. Validation rejects unknown chunk IDs and nonunique exact matches; mutation updates or removes the retrieval index as well as the source file. Reuse that propose/validate/apply separation for memory corrections/deletion, using record IDs and revisions rather than substring deletion in our own store. Moltis also creates a checkpoint before deleting; our product must disclose retained source/backups and avoid silently keeping forgotten content in an operational audit. Source inspection here does not establish purge across every Moltis checkpoint/export. [Validation](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/crates/chat/src/memory_tools.rs#L345), [deletion](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/crates/chat/src/memory_tools.rs#L502), [ambiguity and unreadable-source tests](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/crates/chat/src/memory_tools/tests.rs#L193)

Heartbeat logic has empty-checklist detection, explicit active-hour windows and a no-update sentinel. Useful lesson: deterministic eligibility filtering should precede inference. Do not transplant its 30-minute default or its invalid-hours fallback to always active; our reviews are explicitly enabled and invalid configurations should be actionable errors. Reuse BB schedules rather than importing Moltis's cron service. [Heartbeat implementation](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/crates/cron/src/heartbeat.rs)

## Moltis: why its browser voice loop is not our bootstrap

The inspected browser continuous-VAD path uses energy detection, 250 ms onset debounce and 2,500 ms silence, and skips monitoring during TTS/transcription. That particular path cannot be our low-latency full-duplex foundation without substantial changes. This observation is scoped to browser VAD, not every telephony or voice surface in Moltis. Its explicit resource cleanup and device-health handling remain useful test cases; automatic capture reacquisition must still respect our independent microphone-off state. [Voice input](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/crates/web/ui/src/voice-input.ts#L55), [monitor and cleanup](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/crates/web/ui/src/voice-input.ts#L695)

The current engine retains 600 ms of pre-roll and uses playback generations, but the RMS detector ends on 750 ms of silence and discards utterances shorter than 300 ms. A short “yes” and a thinking pause require measured tests; these defaults should not be treated as semantic turn detection. Its per-window `active` check does not establish exclusivity across two independently activated windows. Barge-in catches and discards backend interruption errors, and speech synthesis reads a complete response before decoding. These are replacement points, not reasons to discard all existing code. [Detector](https://github.com/csells/bb-plugins/blob/758fb4ecc82e5d9e0f3c24dcdceae40de02e8f0d/plugins/jarvis/lib/vad.ts), [engine](https://github.com/csells/bb-plugins/blob/758fb4ecc82e5d9e0f3c24dcdceae40de02e8f0d/plugins/jarvis/lib/engine.ts)

The server hardcodes the brain provider to Claude Code; its interrupt handler only mutes the follower. The skill's ask-and-relay route waits for workers synchronously. Those control paths must be replaced with typed asynchronous BB operations, current interaction binding and observed cancellation. Keep its concise spoken-summary guidance as a persona starting point, while allowing delegation already authorized by Chris. [Server](https://github.com/csells/bb-plugins/blob/758fb4ecc82e5d9e0f3c24dcdceae40de02e8f0d/plugins/jarvis/server.ts), [skill](https://github.com/csells/bb-plugins/blob/758fb4ecc82e5d9e0f3c24dcdceae40de02e8f0d/plugins/jarvis/skills/jarvis/SKILL.md)

## Bootstrap tests derived from this review

Before porting code, lock down five failure scenarios: a cancelled task receiving a late completion; an approval ID already answered on another client; a short approval utterance following a thoughtful pause; a superseded speech response resolving after barge-in; and deletion of a corrected memory while a stale retrieval result is in flight. The expected outcome comes from our product contract, with these source implementations providing concrete failure mechanisms. Fresh staged end-to-end verification remains required.
