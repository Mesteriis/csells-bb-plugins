# Mobile duplex: four conversational SDK source audits

2026-11-14. Source reading only; no SDK integration or hardware acceptance test was performed. Three repositories were cloned at fixed commits. Hume's advertised GitHub repositories returned not-found, so the fourth implementation was inspected through the official npm release's complete bundled code and embedded TypeScript sources. This is four SDK implementations, **not four independent media engines**: Ultravox and ElevenLabs use LiveKit; Vapi uses Daily.

## Ultravox: persistent call media, teardown correctness

**Observed.** `handleSocketMessage` creates `Room({webAudioMix:false})`; captures a local audio track while connecting the room; publishes the microphone; and attaches subscribed remote audio directly to its persistent HTMLAudioElement. Analysis nodes are separate optional branches, not the speaker path. It does not fetch sentence WAVs or shut down the microphone while the agent speaks. See [index.ts L437–487](https://github.com/fixie-ai/ultravox-client-sdk-js/blob/74c10f809867976e24d4e0eb5b40221fd4b02b47/src/index.ts#L437) and [track handling L565](https://github.com/fixie-ai/ultravox-client-sdk-js/blob/74c10f809867976e24d4e0eb5b40221fd4b02b47/src/index.ts#L565).

**Interruption boundary.** Listening/thinking/speaking state and transcripts arrive from the server. `AgentReaction` supports controlling response behavior for injected text, but this client does not implement the server acoustic detector, generation cancellation, or heard-text truncation. Browser media transport supplies duplex, while conversational interruption semantics remain a server contract. Do not equate an interruptible status comment with proof of queue cancellation. [Types and control](https://github.com/fixie-ai/ultravox-client-sdk-js/blob/74c10f809867976e24d4e0eb5b40221fd4b02b47/src/index.ts#L20), [data events](https://github.com/fixie-ai/ultravox-client-sdk-js/blob/74c10f809867976e24d4e0eb5b40221fd4b02b47/src/index.ts#L599).

**Useful donor.** Stop guards reject late socket/data callbacks; capture acquired after stop is explicitly stopped; teardown shares one promise; an unexpected media disconnect becomes an error and closes the call; replacement remote tracks invalidate cached analysis sources. These address exactly the stale-session/late-audio class of failures. [Disconnect/reconnect lifecycle L490–581](https://github.com/fixie-ai/ultravox-client-sdk-js/blob/74c10f809867976e24d4e0eb5b40221fd4b02b47/src/index.ts#L490).

**Do not copy blindly.** Autoplay/context resume rejections and several teardown failures are swallowed. Jarvis should surface these failures and measure actual media progression. `createLocalAudioTrack()` leaves capture defaults to LiveKit: this file does not independently prove realized Android AEC settings or Bluetooth routing.

## Vapi: Daily owns media; application owns lifecycle evidence

**Observed.** `DailyIframe.createCallObject` creates the call with microphone input. Remote tracks are attached to `HTMLAudioElement.srcObject` and `play()` is awaited. The audio element is removed if startup fails. There is no custom sentence player on this normal path. [vapi.ts L321–353](https://github.com/VapiAI/client-sdk-web/blob/6a4838b65a8690a6abfde1dbe4c42f3761959541/vapi.ts#L321), [call creation L672–710](https://github.com/VapiAI/client-sdk-web/blob/6a4838b65a8690a6abfde1dbe4c42f3761959541/vapi.ts#L672).

**Interruption boundary.** App messages are forwarded from Daily. The client exposes `say(message, ..., interruptionsEnabled, interruptAssistantEnabled)`; both flags default false for this explicit injected-speech API. This is not evidence that normal conversation disables interruption. No server VAD/turn-finalizer/LLM cancellation implementation is exposed by this web SDK. Its audio-level-driven speech UI is not a transcript-end detector. [App messages L1128](https://github.com/VapiAI/client-sdk-web/blob/6a4838b65a8690a6abfde1dbe4c42f3761959541/vapi.ts#L1128), [say L1439](https://github.com/VapiAI/client-sdk-web/blob/6a4838b65a8690a6abfde1dbe4c42f3761959541/vapi.ts#L1439).

**Mobile and devices.** It detects mobile user agents and delays one second before joining. That is an observed heuristic, not a proven routing fix. Input changes delegate through `safeSetInputDevicesAsync`; output changes delegate to Daily. The browser's supported routes remain the limit. The optional microphone gain helper captures a second stream and constructs a new graph; it is not needed for Jarvis's first transport integration. [Mobile join L834](https://github.com/VapiAI/client-sdk-web/blob/6a4838b65a8690a6abfde1dbe4c42f3761959541/vapi.ts#L834), [device APIs L1462](https://github.com/VapiAI/client-sdk-web/blob/6a4838b65a8690a6abfde1dbe4c42f3761959541/vapi.ts#L1462).

**Useful donor.** Startup emits named stages with timestamps/durations and error details (call creation, mobile preparation, room join), helping distinguish successful API creation from working call media. Reuse that observability pattern with Jarvis's bounded metadata rules. A hosted Vapi integration would change the service/provider contract; copying this SDK would not supply its hidden conversation engine.

## ElevenLabs: explicit transport split and stale-output suppression

**Observed WebRTC.** `WebRTCConnection` creates a LiveKit Room; selected-microphone acquisition explicitly requests AEC, noise suppression, auto gain and mono. `WebAudioAdapter` attaches remote tracks to hidden HTMLAudioElements, stores them for cleanup, and optionally calls `setSinkId` when supported. Input analysis uses a separate native-rate AudioContext. [Room L334](https://github.com/elevenlabs/packages/blob/5bdaedcc563d4ee418458403ff535575c2a7ffb2/packages/client/src/utils/WebRTCConnection.ts#L334), [capture L851–879](https://github.com/elevenlabs/packages/blob/5bdaedcc563d4ee418458403ff535575c2a7ffb2/packages/client/src/utils/WebRTCConnection.ts#L851), [web adapter L26–74](https://github.com/elevenlabs/packages/blob/5bdaedcc563d4ee418458403ff535575c2a7ffb2/packages/client/src/platform/web/webAudioAdapter.ts#L26).

**Observed interruption.** `VoiceConversation.handleInterruption` switches to listening and calls output.interrupt; audio event IDs older than the last interruption are ignored. The WebSocket output sends an interrupt to its worklet to flush queued buffers and adjusts gain. In contrast, the WebRTC output's interrupt method is explicitly a no-op because the agent/server controls track interruption. This is an important boundary: changing the browser player to WebRTC does not automatically give Jarvis server-side interruption. [VoiceConversation L120–145](https://github.com/elevenlabs/packages/blob/5bdaedcc563d4ee418458403ff535575c2a7ffb2/packages/client/src/VoiceConversation.ts#L120), [WebSocket output L264](https://github.com/elevenlabs/packages/blob/5bdaedcc563d4ee418458403ff535575c2a7ffb2/packages/client/src/platform/web/output.ts#L264), [WebRTC no-op L241](https://github.com/elevenlabs/packages/blob/5bdaedcc563d4ee418458403ff535575c2a7ffb2/packages/client/src/utils/WebRTCConnection.ts#L241).

**Useful donor.** Separate transport-neutral conversation state from platform-specific audio; retain output event IDs to reject late chunks; track playback separately from generation. Its platform tests cover track attachment/volume and connection lifecycle, but were not executed here. Private server VAD, generation abort and history reconciliation cannot be audited from this repo.

## Hume: a real non-WebRTC counterexample, with source availability limits

**Observed from original TypeScript embedded in the npm sourcemap.** `src/lib/useMicrophoneStream.ts` requests AEC/noise suppression/auto gain by default. `useMicrophone.ts` uses MediaRecorder with 100 ms timeslices. `VoiceProvider.tsx` creates one native-rate shared AudioContext for capture analysis and output. `useSoundPlayer.ts` supports a worklet PCM player or decoded buffer queue. Thus full-duplex browser agents do exist using WebSocket/Web Audio; WebRTC is not a logical requirement for duplex, though this does not show that this path works on Chris's phone/car.

**Interruption.** `VoiceProvider.tsx` lines 350–366 handles `user_interruption` by clearing the player queue; if audio was playing, it invokes the interruption callback. `useSoundPlayer.ts` lines 540–560 sends `fadeAndClear` to its worklet, or stops the current buffer source and empties the queue. Microphone capture is not stopped by this operation. This makes output cancellation independent from capture lifecycle. Server-side generation and conversation-history treatment remain unverified.

**Connection.** `useVoiceClient.ts` lines 110–145 uses AbortController and calls the Hume chat connector with `reconnectAttempts:0`; it closes the socket on aborted setup. `VoiceProvider.tsx` defaults verbose transcription true. That setting alone is not proof that local interruption happens on interim transcripts: the inspected handler specifically clears on `user_interruption`.

Source citations for all Hume code above: [exact published module](https://unpkg.com/@humeai/voice-react@0.3.0-beta.6/dist/index.mjs), [original TypeScript sourcemap](https://unpkg.com/@humeai/voice-react@0.3.0-beta.6/dist/index.mjs.map), [package metadata](https://unpkg.com/@humeai/voice-react@0.3.0-beta.6/package.json). Local extracted originals are under `/tmp/jarvis-mobile-audit/hume-react/package/source-extracted/`. This release is suitable for pattern study; unavailable GitHub and redirected EVI documentation make it a weak dependency choice without verifying current support and service access.

## Implications for Jarvis

1. Adopt a supported persistent WebRTC track path as the next integration candidate. Three reviewed SDKs independently expose that application shape, but two share LiveKit and one shares Daily; do not inflate this into three independent proofs of Android routing reliability.
2. Keep capture running during output and interruptions. Avoid coupling a 16 kHz processing graph to the speaker path. Resampling for STT belongs behind a defined boundary.
3. Implement interruption across the whole pipeline: invalidate the response generation, cancel model/TTS work, flush queued PCM before the RTP sender, suppress late frames by generation ID, and reconcile heard versus generated conversation text. None of these client wrappers supplies the whole hidden server contract for our local Alfred/BB backend.
4. Instrument capture, media connection, decoded/playout progress, queue age, cancel acknowledgement and stale-frame drops separately. A server response or UI “speaking” status is not output evidence.
5. Keep the chosen browser/phone/car combination as a separate compatibility measurement. [LiveKit issue 1507](https://github.com/livekit/client-sdk-js/issues/1507) reports different Android Bluetooth outcomes across devices and was closed as not planned. It is adverse ecosystem evidence, not a diagnosis of Jarvis or proof that every current LiveKit release fails.

No inspected SDK exposes a portable JavaScript override for Android communication-device routing. No source review here proves interruption latency, acoustic echo performance, reconnect continuity or audible output on the user's car. Those require real transport integration and measured runs; the architecture can proceed without asking the user to debug another multi-mode matrix.
