# Mobile duplex source audit: four Jarvis agents

Reviewed 2026-11-14. All four projects were selected from Chris's awesome-jarvis README, shallow-cloned into `/tmp/jarvis-mobile-audit`, and their browser implementation files read directly. This is source verification, not hardware execution. Moltis is a negative control, not a fourth successful full-duplex implementation. Leon was cloned during selection but not audited or counted. No Android/car compatibility claim below is established by a desktop/native demo.

## Result

Qwen now provides a concrete browser WebRTC implementation worth reusing as a control/lifecycle reference. Its existing main React UI uses a different WebSocket/Web Audio implementation; one must deliberately select the WebRTC gateway. Paseo and Sutando have valuable interruption and recovery machinery but their browser audio paths resemble the custom PCM/Web Audio approach already failing in Jarvis. Moltis deliberately suppresses listening during playback, so its hands-free mode does not meet our interruption requirement.

## Qwen Audio Agent

**Actual WebRTC browser path.** `BrowserWebRtcConnection` creates an audio `sendrecv` transceiver, obtains ICE servers/policy from its gateway, performs SDP negotiation and listens for the server control data channel. The received audio track becomes an audio element's `srcObject`; a separate analyser branch measures signal without becoming the speaker renderer. A retained microphone stream requests echo cancellation and noise suppression and is attached through `replaceTrack`. Muting changes enabled state rather than reacquiring the mic. Late permission results cannot resurrect a closed connection. [Transport creation and remote track](https://github.com/QwenAudio/qwen-audio-agent/blob/02990dc159d2a6d211f4563daa5120ac9979a0bf/shared/gateway/webrtc-browser.mjs#L22), [microphone lifecycle](https://github.com/QwenAudio/qwen-audio-agent/blob/02990dc159d2a6d211f4563daa5120ac9979a0bf/shared/gateway/webrtc-browser.mjs#L137).

**Interruption.** `interrupt()` clears local playback bookkeeping, mutes the element for 400 ms and sends `response.cancel`. Server `output_audio_buffer.cleared` also clears playback. The fixed temporary mute is a heuristic, not proof all jitter-buffered old audio is gone. Playback receipts distinguish started, ended and cancelled by response ID; ended requires server drain plus a quiet period. Signal-meter evidence remains weaker than acoustic delivery. [Receipts and interruption](https://github.com/QwenAudio/qwen-audio-agent/blob/02990dc159d2a6d211f4563daa5120ac9979a0bf/shared/gateway/webrtc-browser.mjs#L208).

Server provider speech-onset handling starts a correlated input turn and clears response/announcement state; the existing deeper server review documents frontend cancellation and task separation. Neither the browser `response.cancel` nor task cancellation implies heard-only conversation-history truncation. That end-to-end reconciliation still requires a separate explicit contract. [Input runtime](https://github.com/QwenAudio/qwen-audio-agent/blob/02990dc159d2a6d211f4563daa5120ac9979a0bf/server/src/voice/realtime-input-runtime.mjs#L108), [earlier server audit](jarvis-voice-source-review.md).

**Failure/recovery.** ICE gathering and initial connection are bounded; failed or prolonged disconnected states close the connection, rather than silently reconnecting the same call. Autoplay rejection surfaces a user-action error. Cleanup closes tracks, peer and context and releases the server resource. This module does not implement the fuller hotplug reacquisition of the main UI. [Connection/error lifecycle](https://github.com/QwenAudio/qwen-audio-agent/blob/02990dc159d2a6d211f4563daa5120ac9979a0bf/shared/gateway/webrtc-browser.mjs#L30), [cleanup](https://github.com/QwenAudio/qwen-audio-agent/blob/02990dc159d2a6d211f4563daa5120ac9979a0bf/shared/gateway/webrtc-browser.mjs#L238).

**Do not conflate frontends.** The main React hook acquires processed input, resamples it, sends base64 PCM over WebSocket, and connects its capture worklet to context destination. Its independent capture lifecycle debounces device changes and handles ended/muted tracks without reconnecting unrelated session state. These are useful modules but do not make that path WebRTC. [React capture](https://github.com/QwenAudio/qwen-audio-agent/blob/02990dc159d2a6d211f4563daa5120ac9979a0bf/web/src/realtime/useRealtimeVoice.js#L923), [hotplug lifecycle](https://github.com/QwenAudio/qwen-audio-agent/blob/02990dc159d2a6d211f4563daa5120ac9979a0bf/web/src/realtime/microphone-capture.js#L31).

**Reuse:** Apache-2.0 source with project notices to preserve. Prefer lifecycle/receipt ideas or adapting the isolated transport class against our authenticated signaling protocol; adopting its gateway means adding its server media dependency and response protocol, not copying a class alone. [License](https://github.com/QwenAudio/qwen-audio-agent/blob/02990dc159d2a6d211f4563daa5120ac9979a0bf/LICENSE). No specific Android Bluetooth guarantee was found in this inspected module.

## Paseo

**Browser, not native engine.** `audio-engine.web.ts` creates separate capture/playback AudioContexts. It captures with ScriptProcessor4096, computes RMS, resamples to 16 kHz PCM, and connects the processor through a zero-gain destination. Capture requests mono/AEC/noise suppression/AGC. Playback converts PCM or decodes audio, creates a buffer source connected to destination, and stops it on AbortSignal. The native application is a separate path and cannot validate this browser graph. [Capture](https://github.com/getpaseo/paseo/blob/c1d7d56b71960bca17ce86f8d358445b6135b809/packages/app/src/audio/audio-engine.web.ts#L248), [playback](https://github.com/getpaseo/paseo/blob/c1d7d56b71960bca17ce86f8d358445b6135b809/packages/app/src/audio/audio-engine.web.ts#L123).

**Interruption reaches both active and pending output.** The queue separates `stop()` (abort active) from `clearQueue()` (reject pending). Runtime server-speech events reset playback state and invoke both; local volume is not authoritative. Tests explicitly cover late chunks after server interruption and suppression of played acknowledgements for cancelled audio. This is stronger than merely stopping the currently audible sound. [Queue](https://github.com/getpaseo/paseo/blob/c1d7d56b71960bca17ce86f8d358445b6135b809/packages/app/src/audio/playback.ts#L1), [server speech](https://github.com/getpaseo/paseo/blob/c1d7d56b71960bca17ce86f8d358445b6135b809/packages/app/src/voice/voice-runtime.ts#L900), [regressions](https://github.com/getpaseo/paseo/blob/c1d7d56b71960bca17ce86f8d358445b6135b809/packages/app/src/voice/voice-runtime.test.ts#L380).

Server VAD/turn-finalization and synthesis cancellation were covered in [earlier audit](jarvis-voice-source-review.md); that earlier audit used a different commit, so it is historical complementary evidence, not an assertion every server detail was revalidated at this commit. The new browser review establishes cancellation/playback bookkeeping, not heard-only model-history truncation or delegated-process termination. Reuse queue invariants and tests, not this custom renderer as a presumed Android fix. Apache-2.0 except third-party components per [current license](https://github.com/getpaseo/paseo/blob/c1d7d56b71960bca17ce86f8d358445b6135b809/LICENSE). This review did not establish a browser Bluetooth hotplug/reconnect guarantee.

## Moltis: useful negative result

The voice input module supports MediaRecorder and energy VAD. It requests processed capture, uses a 2,500 ms silence threshold, and automatically re-listens. Critically, `onTtsPlay` sets `vadMutedForTts`, stops the recorder and discards pending chunks. Monitoring skips while TTS plays or while the active session is replying. It resumes after output ends with a 400 ms delay. Calling `stopAllAudio` when speech is recognized does not make this duplex because the detector is explicitly suppressed during normal TTS. [Threshold](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/crates/web/ui/src/voice-input.ts#L95), [monitor gating](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/crates/web/ui/src/voice-input.ts#L750), [TTS gating](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/crates/web/ui/src/voice-input.ts#L876).

The monitor attempts suspended-context resume and reacquires ended mic tracks, useful recovery ideas but not the requested simultaneous speech path. No duplex interruption/history reconciliation contract follows from this code. MIT [license](https://github.com/moltis-org/moltis/blob/8a12400dc10551dfb9a6b568414b91a343ef2d5d/LICENSE.md). Do not import its TTS input-muting policy into Jarvis.

## Sutando

**Reusable transport seam.** `web-voice-transport.ts` owns browser capture, WS wire protocol, DSP and playback independently of UI. It acquires processed microphone input, uses ScriptProcessor at device context rate and downsamples for upload. Output PCM is scheduled as AudioBufferSources with a next-play clock and 50 ms restart cushion. An output context requests stream sample rate, falling back to device rate if rejected. This is duplex-capable custom Web Audio, not WebRTC. [Capture](https://github.com/sonichi/sutando/blob/18e997f0781b73aabf5d1f7222110d5a95c73da7/src/web-voice-transport.ts#L1526), [output scheduling](https://github.com/sonichi/sutando/blob/18e997f0781b73aabf5d1f7222110d5a95c73da7/src/web-voice-transport.ts#L1734).

**Critical distinction:** `turn.end` allows final queued audio to drain; `turn.interrupted` immediately stops every active/scheduled source, marks cancellation separately from natural completion and resets the output clock. This prevents both clipped normal endings and old scheduled speech continuing after interruption. [Events](https://github.com/sonichi/sutando/blob/18e997f0781b73aabf5d1f7222110d5a95c73da7/src/web-voice-transport.ts#L1718), [flush](https://github.com/sonichi/sutando/blob/18e997f0781b73aabf5d1f7222110d5a95c73da7/src/web-voice-transport.ts#L1810). This browser transport receives upstream turn decisions; it does not itself prove Gemini/Bodhi's model-history truncation or semantic endpointing behavior. Those dependency internals were not audited here.

**Recovery worth porting.** Connection attempt generation fences late awaits and stale callbacks; capture has a separate generation so recovering the microphone does not kill the still-live socket. It monitors actual capture callback gaps, including gaps hidden by a frozen event loop, observes AudioContext suspension, supports bounded resume/reacquire, and fingerprints input devices so output-only device changes do not force unnecessary capture resets. [Attempt contract](https://github.com/sonichi/sutando/blob/18e997f0781b73aabf5d1f7222110d5a95c73da7/src/web-voice-transport.ts#L36), [capture health](https://github.com/sonichi/sutando/blob/18e997f0781b73aabf5d1f7222110d5a95c73da7/src/web-voice-transport.ts#L1561), [recovery](https://github.com/sonichi/sutando/blob/18e997f0781b73aabf5d1f7222110d5a95c73da7/src/web-voice-transport.ts#L2183), [device change](https://github.com/sonichi/sutando/blob/18e997f0781b73aabf5d1f7222110d5a95c73da7/src/web-voice-transport.ts#L2380).

Reuse state-machine invariants, telemetry and interruption event distinctions. Copying its PCM playback graph would not address our adverse Android evidence. MIT [license](https://github.com/sonichi/sutando/blob/18e997f0781b73aabf5d1f7222110d5a95c73da7/LICENSE). Phone demo claims are not Android/car acoustic validation.

## Concrete implications for Jarvis

1. Select an established WebRTC media implementation while retaining BB orchestration. Qwen's isolated browser gateway confirms that this architecture exists in a directly comparable coding-agent assistant, beyond voice-framework examples.
2. Make response cancellation a cross-layer contract: cancel upstream generation, invalidate response ID, flush server queued PCM, suppress late chunks, stop/clear client playback, and reconcile model history with delivery. None of the reviewed client stop buttons alone establishes all of these.
3. Port lifecycle invariants rather than entire assistant runtimes: stale async generation fencing, separate mic recovery generation, actual callback-gap counters, explicit natural-end versus interruption, and response-scoped playback receipts.
4. Verify acoustic/barge-in behavior separately from transport health. These source audits cannot prove Android Bluetooth routing. Record arrival, decode, queue age, context/capture state, cancellation and reconnect independently, without claiming packet counters mean the user heard speech.

## Qwen server-media follow-through: integration feasibility

The matching server proves this is more than a direct browser-to-cloud-provider bridge. `NativeWebRtcMedia` decodes received RTP through `RTCAudioSink`, resamples PCM to the requested input rate, and emits `onAudio`; output `append({audio, sampleRate, responseId})` accepts base64 PCM, resamples to 48 kHz, and pumps 480-sample mono frames every 10 ms through `RTCAudioSource`, including silence while idle. It exposes `begin`, `append`, `finish`, `clear`, `answer` and `close`. In principle our existing STT and Alfred PCM can connect at this seam. [Native media](https://github.com/QwenAudio/qwen-audio-agent/blob/02990dc159d2a6d211f4563daa5120ac9979a0bf/server/src/transport/webrtc/media.mjs#L58).

The stock route still requires a configured Qwen gateway provider and attaches `WebRtcConnection` to that gateway's session runtime. It translates gateway `audio.delta/audio.done` into media append/finish and mic audio into gateway input events. Therefore installing Qwen unmodified would not automatically use BB's existing STT/model/Alfred flow. Extracting/adapting the media layer is technically possible but requires a BB signaling/control adapter, input segmentation, response ownership and explicit authorization integration. The protocol labels itself experimental; manual audio commit and targeted `response.cancel` are rejected. [Route integration](https://github.com/QwenAudio/qwen-audio-agent/blob/02990dc159d2a6d211f4563daa5120ac9979a0bf/server/src/transport/webrtc/routes.mjs#L65), [gateway protocol](https://github.com/QwenAudio/qwen-audio-agent/blob/02990dc159d2a6d211f4563daa5120ac9979a0bf/server/src/transport/webrtc/protocol.mjs#L15).

**Dependencies and isolation:** optional `qwen-audio-agent-webrtc` v0.1.0 pins `@roamhq/wrtc`0.10.0 and `sharp`0.35.4 with a checked extension API. Its parent launches one disposable child process per peer; the worker receives a narrow environment and no provider credentials. This is a credible Node implementation candidate, but adds native binaries and a matching IPC/worker lifecycle to support. Even audio-only current initialization loads sharp. [Package](https://github.com/QwenAudio/qwen-audio-agent/blob/02990dc159d2a6d211f4563daa5120ac9979a0bf/packages/webrtc/package.json), [process isolation](https://github.com/QwenAudio/qwen-audio-agent/blob/02990dc159d2a6d211f4563daa5120ac9979a0bf/server/src/transport/webrtc/media-process.mjs#L1).

**Cancellation boundary:** client cancel causes protocol `media.clear()` before forwarding upstream cancellation; server `playback.clear/response.interrupted` also clears. The media layer empties its queues, zeros sample count, and adds known response IDs to a blocked set so late chunks are dropped. Both known and blocked sets are bounded to128 IDs; callers still need generation fencing against sufficiently old/reused IDs. The queue allows up to60 seconds of output, too much for our desired low-latency policy without an explicit tighter bound. Server-drained means passed to the native source, not heard. Browser ended is signal-plus-quiet heuristic; no exact consumed-audio timestamp is sent and this protocol does not implement `conversation.item.truncate`. The 400 ms browser mute can suppress buffered tails but cannot prove all in-flight RTP is gone or preserve the beginning of a fast new response. [Queue/flush](https://github.com/QwenAudio/qwen-audio-agent/blob/02990dc159d2a6d211f4563daa5120ac9979a0bf/server/src/transport/webrtc/media.mjs#L167), [cancel forwarding](https://github.com/QwenAudio/qwen-audio-agent/blob/02990dc159d2a6d211f4563daa5120ac9979a0bf/server/src/transport/webrtc/protocol.mjs#L116).

**Selection inference:** this is a useful matched donor for a Node-only design and much more concrete than rewriting RTP pacing ourselves. Pipecat remains a plausible lower-customization choice if its existing Python server pipeline can own STT/turn analysis/TTS together. Compare native Node runtime support and adapter effort against reuse of the existing Python Smart Turn service. Neither choice removes TURN/ICE deployment or our own response-history/authorization responsibilities. Browser disconnect closes after a10-second grace; the transport does not promise transparent reconnect/history continuity. Reconnection needs a new peer/session binding and must not replay old queued audio.
