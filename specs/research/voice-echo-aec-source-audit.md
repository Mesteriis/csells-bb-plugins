# Echo cancellation source audit for the Jarvis spike

2026-11-14 local / November15 UTC. Research only; this audit did not run an acoustic test or change a runtime. The question is how to remove Alfred's acoustic echo while preserving a person speaking over Alfred, without waiting for transcription.

## Decision and rationale

Use reference-based acoustic echo cancellation **before VAD**, followed by speech-onset interruption and separate end-of-turn/STT handling. Keep browser echo cancellation enabled and its persistent received WebRTC track. A server AEC3 stage is a reasonable controlled spike for residual echo, provided render-reference timing is explicit and verified. It is not a universal replacement for correctly integrated endpoint AEC: WebRTC's own [APM interface](https://webrtc.googlesource.com/src/+/refs/heads/main/api/audio/audio_processing.h) says processing belongs close to the audio hardware and defines separate capture/render processing on approximately10ms PCM blocks. Server-side processing normally lacks the local hardware reference.

The echo canceller is not identifying speakers by their words or voice identity. It estimates the contribution of a known rendered waveform to microphone capture; remaining near-end speech can trigger VAD while output is still active. Therefore neither transcript similarity nor minimum word count is the right primary echo-control mechanism. This inference follows directly from the two-signal API above and Speex's explicit [capture/reference/output contract](https://www.speex.org/docs/api/speex-api-reference/group__SpeexEchoState.html).

### Timing contract is the important integration work

Feed the actual paced output reference, resampled consistently to the capture processing rate; do not feed all TTS-generated audio ahead of playback. Capture contains echo after output buffering, network transit, browser jitter/playout, Bluetooth delay and return transit. A server's clock is not the phone's hardware clock. Match reference delivery to a real-time sample timeline and log reference underflow/overflow, capture continuity and delay estimates. Use zero reference during actual silence, not repeated last audio. Keep AEC state/history across utterances and through interruption so in-flight speaker tails still have a reference. Reset on a genuine connection/device discontinuity, not every answer. These are integration recommendations derived from the stateful API, not a verified existing Jarvis implementation.

The [default AEC3 configuration](https://github.com/strands-labs/pywebrtc-audio/blob/1bc860a2051c2b9b3c10b8c778770794b9321d84/vendor/webrtc_audio/api/echo_canceller3_config.h#L29) uses an internal delay estimator and five matched filters. [Buffer sizing](https://github.com/strands-labs/pywebrtc-audio/blob/1bc860a2051c2b9b3c10b8c778770794b9321d84/vendor/webrtc_audio/audio_processing/aec3/aec3_common.h#L69) and [MaxDelay](https://github.com/strands-labs/pywebrtc-audio/blob/1bc860a2051c2b9b3c10b8c778770794b9321d84/vendor/webrtc_audio/audio_processing/aec3/render_delay_buffer.cc#L57) imply153 internal4ms blocks, approximately612ms maximum buffer alignment at default settings. This arithmetic is an inference, not a guarantee of convergence or usable delay search across that whole range. A Bluetooth/network round trip may exceed it. A large `stream_delay_ms` number cannot create missing history. Measure this explicitly before calling a server residual-cancellation design qualified.

The [suppression code](https://github.com/strands-labs/pywebrtc-audio/blob/1bc860a2051c2b9b3c10b8c778770794b9321d84/vendor/webrtc_audio/audio_processing/aec3/suppression_gain.cc#L192) chooses gains using near-end state and echo-to-near-end ratios. That is the relevant existing double-talk machinery to reuse, rather than inventing an application waveform-subtraction algorithm. It still needs representative tests.

## Alternatives and why they are not the first Python spike

SpeexDSP exposes real two-signal echo cancellation and can be integrated using a stable C ABI. Its [manual](https://www.speex.org/docs/manual/speex-manual/node7.html) explains reference/capture timing, sample-clock drift and clipping/nonlinear distortion limitations. The simpler playback/capture pair assumes a two-frame buffer delay; that is not a browser-network/Bluetooth timing solution. It is a reasonable simpler comparison baseline, but replacing AEC3 with Speex would not remove the integration problem. Speex's API documentation and manual were read; no Speex source checkout or executable was tested.

[tonarino/webrtc-audio-processing](https://github.com/tonarino/webrtc-audio-processing) exposes a fuller Rust WebRTC APM integration. [codejq/webrtc-aec](https://github.com/codejq/webrtc-aec) exposes a small C/Python wrapper. Their repository pages were accessed as alternatives, but their implementations were not fully audited in this report and they are not counted as validated substitutes. The Python candidate was inspected in considerably more depth.

## Android/browser limits

Android's official [preprocessing guidance](https://source.android.com/docs/core/audio/implement-pre-processing) says VOICE_COMMUNICATION should have AEC and that routing/gain/preprocessing are selected through product-specific audio policy. The existing [pinned Chromium routing audit](android-duplex-routing.md) records voice-communication input and Bluetooth path selection. Browser `echoCancellation:true` requests processing; it is not proof of the selected physical path's suppression quality. Keep capture and remote playback on the standard WebRTC route and record realized capture settings. Do not solve echo by switching off capture while Alfred speaks; that would remove double-talk.

The current digital feedback browser harness deliberately bypasses the hardware/browser capture chain by supplying a generated MediaStream. Its failure shows the server needs reference-aware processing for that test; it does not prove Chrome's physical AEC failed. Conversely, passing a digital AEC test does not establish physical Android/car performance.

## Required spike evidence

1. **Far-end only:** real Alfred speech, delayed/attenuated filtered feedback into capture, no user speech. Measure suppression and VAD false starts throughout a whole reply, including initial convergence and tail.
2. **Near-end only:** ordinary user speech and short controls, including words Alfred recently used. Verify preserved speech and correct transcription. Matching words must not be rejected as echo.
3. **Double-talk:** independently sourced near-end speech plus Alfred echo, overlapping in time at several level ratios and delays. Assert near-end onset produces interruption without waiting for final transcript, preserve onset/preroll, and measure onset-to-last-old-audio, not only post-cancel tail.
4. **Path change:** delay shift, gain change, packet timing jitter and clock drift. Report convergence and errors; do not hide them behind a successful final transcript.
5. **Actual candidate:** keep the real Pipecat/TURN/STT/director/Alfred path; test stimuli are fixtures, not stand-in services. Separate component DSP evidence, browser RTP evidence, and physical car evidence. No raw personal microphone recording is required for deterministic fixtures.

The definition of success includes **preserving** overlapping speech. A solution that silences every input during playback achieves excellent echo suppression and completely fails the user's requirement.

## Follow-up: measure preserved near-end speech, not waveform identity

The implementation investigation reported strong echo suppression but sample-waveform correlation around0.68–0.73 after best constant-lag alignment. An initial correlation>0.75 assertion failed. That failure should remain in the evidence; lowering its threshold to the observed result would not establish speech preservation.

The original [STOI paper, Taal et al.2011](https://sps.ewi.tudelft.nl/pubs/Taal2011_1.pdf) evaluates intelligibility of noisy and time-frequency-weighted speech using short-time frequency-band envelopes. This is materially different from one Pearson correlation over signed waveform samples. The accessible [pySTOI implementation](https://raw.githubusercontent.com/mpariente/pystoi/master/pystoi/stoi.py) resamples to10kHz, removes silent frames, forms15 third-octave magnitude bands, and compares30-frame envelope segments. It requires enough non-silent duration; it warns and returns a tiny sentinel when insufficient. Do not score a single very short “yes” as though it supplied a valid independent STOI estimate. Pin the exact package/source used in measurement; this report inspected the main-branch source, not a locally executed version.

There is a concrete possible explanation for reduced waveform similarity: the vendored [high-pass filter](https://github.com/strands-labs/pywebrtc-audio/blob/1bc860a2051c2b9b3c10b8c778770794b9321d84/vendor/webrtc_audio/audio_processing/high_pass_filter.cc#L20) is a second-order100Hz Butterworth biquad, whose source exposes nontrivial denominator coefficients. Such an IIR changes frequency-dependent phase as well as magnitude; shifting by one constant delay cannot undo that. Suppression stages additionally change spectral gains over time. **This is a plausible explanation, not a diagnosis of the observed numbers.** Measure an ablation rather than attributing every mismatch to harmless filtering.

Use four fixed-condition paths with the same source speech and alignment policy:

1. Original clean near-end reference.
2. Near-end alone through the exact configured AEC/high-pass/noise-suppression chain, with zero render reference.
3. Unprocessed near-end plus delayed/filtered echo.
4. The same mixture after the exact candidate processing chain.

Report STOI against clean speech for paths2–4, along with path4 minus path2, active-speech gain, raw waveform correlation, and lag. This distinguishes inherent processing effects from additional double-talk damage. For correlation-only diagnostics, compare the processed mixture to processed clean baseline as an extra measurement, while retaining clean-reference STOI to avoid hiding distortion. No cited source supplies a universal STOI>=0.9 or waveform-correlation>=0.75 product acceptance threshold.

Microsoft's [AEC Challenge evaluation paper](https://www.microsoft.com/en-us/research/wp-content/uploads/2021/08/245_Full-Paper.pdf) explicitly limits ERLE to single-talk quiet conditions and finds that ERLE/PESQ do not reliably capture subjective quality on realistic recordings. Do not report the echo-only suppression number as a double-talk quality score. Its [AECMOS work](https://www.microsoft.com/en-us/research/publication/aecmos-a-speech-quality-assessment-metric-for-echo-impairment/) separately evaluates echo and other degradation; the paper/tool page is relevant follow-up, but its local model was not fetched or executed here.

Practical spike acceptance should remain behavioral and independently specified: real STT recognizes the known independent near-end utterance and its important control words under the fixed overlap/delay/level scenarios; onset/preroll is retained; echo alone dispatches no input; and speech-onset-to-old-audio-stop meets the declared latency criterion. Use STOI and baseline-relative degradation to quantify limitations rather than replacing one arbitrary cutoff with another. A passed single synthesized sentence is a narrow fixture result, not broad human-intelligibility or car qualification. A controlled device listening assessment and a varied speech corpus remain distinct from these automated checks.

## Follow-up: reference timing over remote WebRTC

A later candidate experiment reportedly succeeded with120ms injected echo but lost suppression after a silent interval at250ms injected echo and quieter near-end speech. Zero reference FIFO underflows and a10–20ms FIFO backlog do **not** establish the physical or looped render-to-capture delay. They measure an application queue, whereas the reference path includes receiver jitter buffering, playout, imposed/acoustic delay and return capture. Excess delay is a plausible cause alongside alignment discontinuity, differing sample clocks, and state/convergence behavior. The RMS observations alone do not distinguish them.

The standards-backed primary architecture remains endpoint AEC. [RFC7874 section5](https://www.rfc-editor.org/rfc/rfc7874.html#section-5) recommends echo control in the endpoint, explicitly considers independent capture/playback clocks, and treats far-end cancellation as an optional additional facility. The current browser persistent native WebRTC playback path should therefore be retained while diagnosing actual realized capture processing; a server residual canceller is an additional mechanism, not proof endpoint AEC is unnecessary.

For the current server-reference experiment, the next discriminating measurement is an in-memory sample-indexed capture of **known test fixtures only**: paced render reference, returned echo-only capture before/after the failed interval, and actual array lengths/timestamps delivered to AEC3. Estimate lag in sufficiently excited echo-only windows and compare the exact same recording under unchanged AEC3 and under a known coarse reference offset. Preserve the complete before/after window; do not select only the converged period. Confirm onset, pause, packet timing and sample counts. No personal microphone recording is implied.

Coarse time-delay compensation preceding AEC is an established signal-processing architecture: [Pfeifenberger et al., Interspeech2021](https://www.isca-archive.org/interspeech_2021/pfeifenberger21_interspeech.pdf) uses GCC-PHAT time-delay compensation followed by linear AEC and a residual postprocessor. This supports testing a measured coarse offset when the default AEC3 search range is exceeded. It does not justify adopting an unvalidated adaptive delay heuristic on every noisy/double-talk frame. Require confidence, bound adjustments, distinguish clock drift from discontinuous delay changes, and test reacquisition. No implementation from that paper was downloaded or run for this audit.

Sending synchronized microphone and render-reference channels from the browser is another **experimental** architecture. A [ChannelMergerNode](https://www.w3.org/TR/webaudio/#ChannelMergerNode) can place the two signals in one graph's frames, reducing differential uplink jitter if they survive the encoder and decoder together. However:

- A tap of the decoded remote track is not a measurement of the physical speaker sample. Rendering through a native audio element and tapping through a separate AudioContext can have different scheduling; Bluetooth/output delay remains. The [Web Audio outputLatency definition](https://www.w3.org/TR/webaudio/#dom-audiocontext-outputlatency) is device-dependent and can change during a context lifetime.
- A browser graph adds a new capture/processing path, including buffering and sample-rate conversion. It must not duplicate speaker playback or send the reference back as user speech.
- Two-channel Opus negotiation requires explicit handling. [RFC7587 sections6/7.1](https://www.rfc-editor.org/rfc/rfc7587.html#section-7.1) defines stereo receive preference with default0 and says a single-destination sender must not use stereo when the receiver specifies0. `opus/48000/2` alone does not demonstrate two preserved channels. `sprop-stereo` describes expected sender content, not a channel-preservation guarantee.
- Prove channel separation and independent signal preservation after the actual browser encoder and server decoder. Pipecat input downmixing must not run before separation. Lossy encoding, changing channel configuration and missing references must produce explicit diagnostics.

Recommendation: measure and fix the existing reference timeline first; choose the paired browser-reference transport only if the measured server timing cannot be made reliable with a small, bounded adaptation. Treat either as a falsifiable spike. The sources inspected here do not establish that transmitting mic/reference as stereo is a standard production mobile-agent practice or a proven cure for this phone. Retain the native endpoint-AEC path and its device observability throughout.

## Correction: render buffer capacity is not matched-filter search coverage

Further fixture instrumentation reportedly measured530–532ms render-to-capture echo lag with coherence approximately0.87 shortly before false VAD. These reported runtime observations were supplied by the implementation agent; this source audit independently verifies the relevant arithmetic, not the observation itself.

The earlier approximate612ms value describes allocated render-delay capacity, **not the actual matched-filter bank's search coverage**. At the pinned wrapper revision, [matched_filter.cc constructor/update](https://github.com/strands-labs/pywebrtc-audio/blob/1bc860a2051c2b9b3c10b8c778770794b9321d84/vendor/webrtc_audio/audio_processing/aec3/matched_filter.cc#L303) creates `N` filters, each32 internal blocks long, and advances successive filter origins by24 blocks. The update loop starts at origin0 and visits indices0 throughN−1. One internal64-sample16kHz block is4ms. Nominal bank coverage is therefore `(N−1)×96ms +128ms`:

| Filter count | Nominal search span | Largest locally reliable peak, relative to the current render-buffer origin |
| --- | --- | --- |
| 5, default | 512ms | 509.25ms |
| 10 | 992ms | 989.25ms |
| 12, arithmetic only | 1184ms | 1181.25ms; unsafe with this source's update implementation |

The strict [reliability condition](https://github.com/strands-labs/pywebrtc-audio/blob/1bc860a2051c2b9b3c10b8c778770794b9321d84/vendor/webrtc_audio/audio_processing/aec3/matched_filter.cc#L394) requires local lag greater than2 and less than `filter_size−10`. With downsampling4, a filter has512 taps at4kHz; its final accepted integer tap is501, or125.25ms after its origin. Confidence and excitation tests further constrain actual accepted estimates. These arithmetic bounds are not guarantees of accurate estimation over the entire interval.

The similarly named [GetMaxFilterLag](https://github.com/strands-labs/pywebrtc-audio/blob/1bc860a2051c2b9b3c10b8c778770794b9321d84/vendor/webrtc_audio/audio_processing/aec3/matched_filter.h#L111) returns `N×shift+window` for supporting allocation. It is one shift larger than the final filter's actual endpoint. Using that accessor or render-buffer capacity to infer search coverage would overstate the reachable lag.

**Use10 as the first controlled native-configuration comparison, not12.** Although [configuration validation](https://github.com/strands-labs/pywebrtc-audio/blob/1bc860a2051c2b9b3c10b8c778770794b9321d84/vendor/webrtc_audio/api/echo_canceller3_config.cc#L112) allows counts up to5000, [the actual update loop](https://github.com/strands-labs/pywebrtc-audio/blob/1bc860a2051c2b9b3c10b8c778770794b9321d84/vendor/webrtc_audio/audio_processing/aec3/matched_filter.cc#L400) asserts count<=10 and has a per-filter dump switch whose default calls `RTC_NOTREACHED()`. A valid configuration schema is insufficient proof that12 is supported safely by this vendored implementation.

Setting `config.delay.num_filters=10` at the wrapper's constructor/reset factory sites keeps the existing AEC3 algorithm and extends its native filter bank. It increases processing and memory, so measure CPU/frame latency. The530–532ms fixture lag is consistent with being outside the default bank, but physical/application lag and the internal render-buffer read origin are not automatically identical. A controlled5-versus10 run of the same failure fixture, with near-end preservation and interruption tests unchanged, is necessary before claiming the search bound caused the failure or the configuration solves it. Do not describe the untested12-filter variant as working.

The implementation agent reported that a short independent “Wait” could be almost eliminated despite microphone input containing no actual echo, while the render reference still contained Alfred. A later controlled offline comparison of the same short speech showed near-end RMS gain approximately0.227 with extra server noise suppression enabled versus0.798 with it disabled. ### Transparent mode exists in the pinned engine

The pinned [AecState::TransparentMode](https://github.com/strands-labs/pywebrtc-audio/blob/1bc860a2051c2b9b3c10b8c778770794b9321d84/vendor/webrtc_audio/audio_processing/aec3/aec_state.cc#L347) already detects cases without a useful acoustic echo path. It does not transparently pass near-end immediately: its fallback requires more than6seconds of strong, nonsaturated active render, plus conditions concerning recent convergence/finite echo-path observations. Active-render duration is not elapsed wall time; speech pauses do not necessarily advance it. The [residual estimator](https://github.com/strands-labs/pywebrtc-audio/blob/1bc860a2051c2b9b3c10b8c778770794b9321d84/vendor/webrtc_audio/audio_processing/aec3/residual_echo_estimator.cc#L142) uses render-derived echo-power estimates before a usable linear estimate; default path amplitude gain is1.0, versus0.01 in transparent mode. This is a concrete mechanism that can conservatively suppress near-end speech when a reference is present but actual echo is absent. It is not proof that it explains every observed short-control failure.

Current upstream [transparent_mode.cc](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/audio_processing/aec3/transparent_mode.cc) also contains an optional HMM classifier controlled by `WebRTC-Aec3TransparentModeHmm`. Thus “the wrapper has no transparent mode” would be false. Upgrading to current APM is not by itself verified to solve the fixture either. A useful isolated test compares identical no-echo short speech early in render activity and after sufficient active-render convergence, with transparent/usable-linear state observed. No amplitude-triggered bypass is justified by this finding.

### Noise-suppressor ordering is not automatically an API bug

The [wrapper AudioProcessor](https://github.com/strands-labs/pywebrtc-audio/blob/1bc860a2051c2b9b3c10b8c778770794b9321d84/bindings/webrtc_audio_bindings.cpp#L871) runs NS Analyze before AEC ProcessCapture, then NS Process afterward. Current primary [WebRTC audio_processing_impl.cc](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/audio_processing/audio_processing_impl.cc) uses that same order by default. It optionally analyzes the linear-AEC output when configured and available; the Python wrapper does not expose that option. Therefore the mere fact that NS analyzes earlier audio and processes AEC-cleaned audio is not evidence of misuse.

There are differences worth retaining as audit findings: normal APM applies the configured high-pass stage before NS analysis, whereas the wrapper applies it later. The wrapper also invokes NS Analyze before splitting capture frequency bands; at16kHz the single band aliases the full-band buffer, whereas32/48kHz would require separate scrutiny. These differences were found in source, not established as the cause of this16kHz failure. Do not rewrite the DSP pipeline based on that suspicion.

The controlled NS-on/off result supports the minimal next experiment already selected by the implementation agent: **disable the redundant server noise suppressor through its supported configuration while retaining AEC3 and browser processing**, then rerun the same short-control, echo-only, and overlapping-speech tests. This preserves the established canceller rather than adding an amplitude bypass or tuning suppression thresholds until a single fixture passes. Near-end intelligibility, false echo triggers and onset-to-stop latency must all remain visible; reduced suppression is not automatically an improvement if self-triggering returns.
