# Android browser duplex audio: routing-source investigation

Date: 2026-11-14. Research-only; no implementation changes. Question: why does Jarvis's car playback work with capture off but fail or arrive late with capture active, and which browser spikes discriminate viable full-duplex routes?

## Evidence, not diagnosis

Chris confirms microphone-off playback is audible, microphone-on playback still fails, and an earlier response eventually arrived several minutes late. Latest provided phone trace: visible page, native media reports playing, but a 1.86-second clip does not finish and times out roughly 12 seconds later. PCM has nonzero energy. This narrows investigation beyond server synthesis; it does **not** prove a particular Android, Bluetooth, browser, or head-unit defect. A playing event alone is not evidence of audio reaching speakers. Actual Android version, phone model, car/head-unit model and effective input-device selection remain unrecorded.

## Primary-source findings

Chromium source was inspected at main commit `98a553cfaebdf2a7a81803e1dbc9613070e8c06e`. This is a pinned research reference, not proof that Chrome/157.0.0.0 on Chris's phone contains exactly this revision or feature configuration.

- On the phone routing path, the first processed input stream enables communication mode. Closing the last input restores mode. The low-latency output factory chooses media versus voice-communication usage when creating an output stream. Input-device selection can select a combined input/output communication route; output enumeration may expose only default. Consequently, “select phone microphone while keeping car speakers” is not guaranteed to be independently controllable. [Audio manager source](https://chromium.googlesource.com/chromium/src/+/98a553cfaebdf2a7a81803e1dbc9613070e8c06e/media/audio/android/audio_manager_android.cc)
- The newer per-stream selection feature is enabled in feature definitions, but its effective predicate also requires an Android **desktop** device, along with AAudio input/output. Do not infer phone availability from the feature's default alone. [Feature definitions](https://chromium.googlesource.com/chromium/src/+/98a553cfaebdf2a7a81803e1dbc9613070e8c06e/media/audio/audio_features.cc), [effective predicate](https://chromium.googlesource.com/chromium/src/+/98a553cfaebdf2a7a81803e1dbc9613070e8c06e/media/audio/android/audio_manager_android.cc#374)
- The Java layer explicitly sets Android `MODE_IN_COMMUNICATION`, tracks communication-stream volume, and restores `MODE_NORMAL` on shutdown. Media volume is therefore not sufficient evidence for the communication path. [Java implementation](https://chromium.googlesource.com/chromium/src/+/98a553cfaebdf2a7a81803e1dbc9613070e8c06e/media/base/android/java/src/org/chromium/media/AudioManagerAndroid.java)
- AAudio uses a voice-communication input preset when echo cancellation is requested and a generic preset otherwise; it deliberately avoids an unprocessed preset because it can produce quiet/silent input. [AAudio wrapper](https://chromium.googlesource.com/chromium/src/+/98a553cfaebdf2a7a81803e1dbc9613070e8c06e/media/audio/android/aaudio_stream_wrapper.cc#512)
- Chromium's 2024 fix explicitly associates Bluetooth microphone activation with an A2DP-to-SCO output transition. This explains why a working YouTube/media path does not establish a working duplex path. It does not prove that this historical bug is the current incident. [Original change](https://chromium.googlesource.com/chromium/src/+/78d0de138346e6edfc8c33bdd22c45b3eec4f3d0)
- Android exposes communication-device control to native applications; browser JavaScript does not directly receive `AudioManager.setCommunicationDevice`. Browser constraints and returned track settings are the available experimental controls. Requested constraints and realized settings are different; record `getSupportedConstraints()`, capabilities where available, and `track.getSettings()`. [Android API](https://developer.android.com/reference/android/media/AudioManager#setCommunicationDevice(android.media.AudioDeviceInfo)), [capture specification](https://w3c.github.io/mediacapture-main/#constrainable-interface)

## Discriminating spikes

These are predictions to test, not confirmed fixes:

| Spike | Controlled difference | What a positive result establishes |
|---|---|---|
| Microphone-first output creation | Open capture, then create a fresh native-rate output context/stream; compare output-before-input | Stream creation order matters on this device; rebuild output after route activation |
| All capture processing off | Request echoCancellation, noiseSuppression and autoGainControl false; confirm realized settings; keep capture live | Processed capture / communication routing is implicated, subject to actual selected route |
| Explicit input selection | Enumerate after permission; test default, Bluetooth, and built-in candidates individually | Which exposed route works; **not** proof of independent input/output routing |
| Actual WebRTC receive track | Compare persistent remote MediaStream playback to WAV/Blob and WebAudio output while sending microphone audio | Whether the browser's real-time communication renderer avoids the failure |
| Stop versus disable | Compare `track.enabled=false` to `track.stop()` and full capture teardown | Whether hardware capture ownership, rather than nonzero microphone samples, controls the failure |

All-effects-off is a diagnostic alternative, not production acceptance: it removes requested echo cancellation, so loudspeaker echo and false barge-ins must be measured. Bluetooth selection may still activate SCO independently. A persistent WebRTC receive track is a stronger architectural candidate than repeatedly reopening sentence media, but WebRTC does not grant an application arbitrary control of Android routes. A same-device peer loop is only a renderer probe; remote duplex acceptance needs a real network endpoint and actual phone/car output.

For every variant record: exact browser/OS, capture constraints/settings, audio context sample rate/state, media time progression, fresh native media creation order, microphone state, device-change events, wall and monotonic times, and user-reported audibility. Do not export device labels/IDs or raw audio by default. Require continuous capture during audible output and a successfully recognized interruption; mic-off audio or headless Chromium alone cannot close full-duplex acceptance.

## Follow-up: forced 16 kHz capture context and silent output graph

The implementation detail reported for investigation is a 16 kHz capture `AudioContext` whose worklet emits silence into `context.destination`, alongside native media playback. This is a useful confounding variable to remove, **not a demonstrated cause** of the native player's stall. No reviewed primary source establishes that this configuration causes Android native media to stop advancing.

The Web Audio specification requires resampling when a context's requested rate differs from the output device rate, and warns that this may substantially affect latency. Omitting `sampleRate` uses the output device's default rate. Thus native-rate capture is a justified experimental baseline; it does not by itself establish the correct Android communication route. Any downstream detector or STT encoder expecting 16 kHz must receive explicitly resampled data rather than native-rate samples mislabeled as 16 kHz. [AudioContext construction](https://webaudio.github.io/web-audio-api/#dom-audiocontext-audiocontext)

A capture-only worklet can use one input and zero outputs; only the combination of zero inputs and zero outputs is prohibited. The graph need not connect to the audible destination for input processing. This is supported both by the specification and by the inspected Chromium implementation: `AudioWorkletHandler::UpdatePullStatusIfNeeded` adds nodes with no connected outputs to automatic pulling, and node creation calls it even without a `connect()` call. Keep the processor active by returning `true` and verify continuing captured-frame counters and nonzero microphone energy on the actual phone. [Worklet options](https://webaudio.github.io/web-audio-api/#dom-audioworkletnodeoptions), [Chromium handler](https://chromium.googlesource.com/chromium/src/+/98a553cfaebdf2a7a81803e1dbc9613070e8c06e/third_party/blink/renderer/modules/webaudio/audio_worklet_handler.cc), [Chromium node construction](https://chromium.googlesource.com/chromium/src/+/98a553cfaebdf2a7a81803e1dbc9613070e8c06e/third_party/blink/renderer/modules/webaudio/audio_worklet_node.cc)

Removing a destination connection does **not** prove that the context itself relinquishes its hardware output sink. Chrome separately documents a silent sink, `await context.setSinkId({type: "none"})`, for processing microphone input without audible output while its clock continues. Feature-detect the method, catch and record rejection, and verify effective sink state on this Android browser; generic Chrome documentation is insufficient proof of support for the phone's configuration. This is a separate spike, not an assumption to embed in the main path. [Chrome's silent-sink documentation](https://developer.chrome.com/blog/audiocontext-setsinkid#render-audio-with-a-muted-audiocontext)

Use a four-cell test with identical capture constraints, microphone-first ordering, and the same native-media sentence: (1) 16 kHz plus destination, (2) native rate plus destination, (3) 16 kHz plus zero-output worklet, (4) native rate plus zero-output worklet. Record capture frame flow, context time, media time, ended/timeout, and audible onset. The native-rate analyser-without-destination probe is a useful initial simplification, but changing both rate and graph together cannot attribute a positive result to either. If all four stall, that weakens this graph hypothesis and increases the value of the actual WebRTC receive-track and communication-route probes above.
